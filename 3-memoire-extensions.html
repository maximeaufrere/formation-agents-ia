09

Mémoire, gestion du contexte et RAG

Comprendre comment un agent « se souvient » et accède à de la connaissance malgré une fenêtre limitée.

Rappel : le modèle n'a pas de mémoire propre, seulement ce qui est dans son contexte. Un agent qui travaille longtemps accumule vite des milliers de tokens. Trois façons de s'en sortir :

Court terme

L'historique

Le fil de la tâche en cours. Disparaît à la fin de la session.

Résumé

La compaction

Quand le contexte approche de sa limite, on le résume pour garder l'essentiel.

Long terme

Les notes

L'agent écrit dans des fichiers ou une base et les relit à la prochaine session.

Pour accéder à des documents trop volumineux pour le contexte, on utilise le RAG (Retrieval-Augmented Generation) : on cherche les passages pertinents, on les ajoute à la question, puis le modèle répond à partir d'eux.

Le modèle répond à partir des extraits retrouvés, pas de sa seule mémoire.

Analogie : l'examen à livre ouvert

Plutôt que de faire réciter toute la documentation par cœur, on permet au modèle de feuilleter le bon chapitre avant de répondre. Résultat : des réponses à jour, vérifiables (on cite la source) et basées sur tes propres documents.

Le pipeline RAG classique

  1. Découper (chunking) les documents en passages de quelques centaines de tokens, avec un léger chevauchement.
  2. Vectoriser chaque passage : un embedding transforme le texte en liste de nombres représentant son sens. Les passages de sens proche donnent des vecteurs proches.
  3. Indexer les vecteurs dans une base vectorielle.
  4. Interroger : vectoriser la question, récupérer les k passages les plus proches.
  5. Générer : fournir ces passages au modèle avec la consigne de répondre uniquement à partir d'eux et de citer ses sources.

Deux écoles de recherche

Recherche sémantique

Par embeddings. Trouve des idées proches même sans mots communs. Demande un index à maintenir.

Recherche par mots-clés

Type BM25, grep. Précise pour les noms, codes, identifiants. Pas d'index vectoriel.

Beaucoup de systèmes combinent les deux (recherche hybride). À l'inverse, certains agents, dont les agents de code, privilégient la recherche agentique : ils cherchent eux-mêmes avec des outils (lister, grep, lire un fichier), affinent leur requête selon les résultats, sans construire d'index.

Techniques de gestion du contexte

  • Compaction : résumer l'historique et repartir d'un contexte propre contenant le résumé.
  • Notes persistantes : fichier de suivi (NOTES.md, liste de tâches) que l'agent relit après un reset.
  • Isolation par sous-agents : une recherche volumineuse est faite dans un contexte séparé qui ne renvoie qu'un résumé (chapitre 12).

Embeddings et similarité

La proximité de deux vecteurs a et b se mesure souvent par la similarité cosinus : cos(a, b) = (a · b) / (‖a‖ ‖b‖), proche de 1 quand les sens sont voisins. Les bases vectorielles utilisent des index approchés (HNSW, IVF) pour chercher parmi des millions de vecteurs en quelques millisecondes, au prix d'un rappel légèrement inférieur à 100 %.

Ce qui fait réussir ou échouer un RAG

  • La qualité de la récupération prime. Si le bon passage n'est pas dans les k résultats, le meilleur modèle ne peut rien. Mesure le rappel@k sur un jeu de questions avec réponses connues, avant de toucher au prompt de génération.
  • Taille des passages : trop petits, ils perdent le contexte ; trop grands, ils diluent le sens. Découper selon la structure du document (titres, paragraphes) plutôt qu'à longueur fixe.
  • Contexte ajouté aux passages : préfixer chaque passage d'une courte description de sa provenance (« Procédure congés, section 3 ») améliore nettement la récupération.
  • Reclassement (reranking) : récupérer 50 candidats rapidement, puis les reclasser avec un modèle plus précis pour n'en garder que 5.
  • Évaluer séparément la récupération (a-t-on trouvé le bon passage ?) et la génération (la réponse est-elle fidèle aux passages ?).
  • Sécurité : les documents indexés sont du contenu non fiable (injection de prompt) et les droits d'accès doivent être respectés : un utilisateur ne doit jamais récupérer un passage qu'il n'a pas le droit de lire.
RAG ou recherche agentique ?

Le RAG vectoriel excelle sur de gros corpus de texte et des questions floues. La recherche agentique (outils + itération) excelle sur des corpus structurés (code, fichiers, bases) et des questions précises, et évite l'index à tenir à jour, au prix de plus d'appels. Les deux se combinent.

À retenir
  • Le modèle n'a pas de mémoire propre : historique, compaction, notes dans des fichiers.
  • RAG : chercher les passages pertinents, les ajouter à la question, répondre à partir d'eux.
  • La qualité de la récupération prime sur celle de la génération.
  • Les agents de code cherchent eux-mêmes (recherche agentique) au lieu d'indexer.

Suite : Chapitre 10 · MCP : brancher des outils

10

MCP : une prise universelle pour les outils

Comprendre le protocole MCP, son architecture et ses risques.

Chaque outil (agenda, messagerie, base de données, ticketing) a sa propre interface. Sans standard, il faudrait écrire une intégration sur mesure pour chaque couple « application d'IA × outil ».

Le MCP (Model Context Protocol) est un protocole ouvert, lancé par Anthropic et repris par une bonne partie du secteur. Il définit une façon commune de décrire et d'appeler des outils et des sources de données.

Analogie : la prise USB-C

Avant l'USB-C, chaque appareil avait son chargeur. Avec une prise commune, n'importe quel appareil se branche sur n'importe quel port. Avec MCP, un serveur MCP (par exemple celui de ton outil de tickets) se branche à tout client MCP (un assistant, un agent, un éditeur de code).

Serveur MCP

Petit programme qui expose les capacités d'une application.

Client MCP

L'application d'IA qui s'y connecte et met les outils à disposition du modèle.

Architecture

  • Hôte : l'application d'IA (Claude Code, un assistant de bureau, un IDE).
  • Client : composant de l'hôte qui maintient une connexion avec un serveur.
  • Serveur : expose des capacités. Il peut tourner sur ta machine ou être distant.

Ce qu'un serveur peut exposer

PrimitiveRôlePiloté par
Tools (outils)Actions exécutables (créer un ticket, lancer une requête).Le modèle
Resources (ressources)Données à lire (fichiers, enregistrements, schéma de base).L'application / l'utilisateur
PromptsModèles de prompts réutilisables proposés à l'utilisateur.L'utilisateur

Deux modes de transport

  • stdio : l'hôte lance le serveur comme un processus local et lui parle par l'entrée/sortie standard. Simple, local.
  • HTTP (streamable) : serveur distant, avec authentification (OAuth le plus souvent). Adapté aux services hébergés partagés.

Sous le capot : JSON-RPC 2.0

MCP échange des messages JSON-RPC. Après une phase d'initialisation (négociation de version et de capacités), l'hôte liste puis appelle les outils :

→ {"jsonrpc":"2.0","id":1,"method":"tools/list"}
← {"jsonrpc":"2.0","id":1,"result":{"tools":[
     {"name":"chercher_salles","description":"Liste les salles libres",
      "inputSchema":{"type":"object","properties":{"date":{"type":"string"}},"required":["date"]}}]}}

→ {"jsonrpc":"2.0","id":2,"method":"tools/call",
   "params":{"name":"chercher_salles","arguments":{"date":"2026-10-27"}}}
← {"jsonrpc":"2.0","id":2,"result":{"content":[{"type":"text","text":"Rhône (10 places)"}]}}

Un serveur minimal en Python

serveur_salles.py 
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("salles")

@mcp.tool()
def chercher_salles(date: str, places_min: int = 1) -> str:
    """Liste les salles libres à une date (AAAA-MM-JJ)."""
    return "Rhône (10 places), Saône (8 places)"

if __name__ == "__main__":
    mcp.run()          # transport stdio par défaut

La docstring et les annotations de type deviennent automatiquement la description et le schéma de l'outil.

Risques et coûts propres à MCP

  • Coût en contexte : les définitions de tous les outils de tous les serveurs connectés sont injectées dans le contexte. Dix serveurs bavards peuvent consommer des dizaines de milliers de tokens avant le premier message. Active seulement ce dont tu as besoin.
  • Chaîne d'approvisionnement : un serveur MCP est du code exécuté avec tes droits : n'installe que des serveurs de confiance (chapitre 13).
  • Empoisonnement d'outil : la description d'un outil est lue par le modèle. Une description malveillante peut contenir des instructions cachées. Même logique que l'injection de prompt.
  • Portée des droits : un jeton d'accès trop large donne à l'agent plus de pouvoir que nécessaire. Utilise des jetons à portée minimale, en lecture seule quand c'est possible.
  • Combinaison dangereuse : un serveur qui lit des données privées + un autre qui lit du contenu public non fiable + un troisième qui peut envoyer vers l'extérieur forment la « triade létale » (chapitre 13).
À retenir
  • MCP est un standard ouvert pour brancher des outils et des données à une application d'IA.
  • Un serveur expose des outils, des ressources et des prompts ; un client s'y connecte.
  • Les définitions d'outils coûtent du contexte : n'active que le nécessaire.
  • Un serveur MCP est du code exécuté avec tes droits : installe uniquement des sources de confiance.

Suite : Chapitre 11 · Skills : transmettre un savoir-faire

11

Skills : transmettre un savoir-faire

Savoir ce qu'est une skill, quand en écrire une, et en quoi elle diffère d'un outil.

Un outil donne une capacité (« je peux lire un PDF »). Une skill donne un savoir-faire : un mode d'emploi écrit en langage naturel, avec éventuellement des scripts et des modèles de documents, qui explique comment réussir un type de tâche (« voici comment rédiger un compte rendu aux normes de l'entreprise »).

Analogie : le classeur de procédures

Une nouvelle recrue connaît le métier en général. Les skills sont le classeur de procédures de ton équipe : elle sort la bonne fiche au bon moment au lieu de tout apprendre par cœur.

L'intérêt : l'agent ne charge une skill que lorsqu'elle est utile. On peut en avoir des dizaines sans saturer le contexte.

Structure d'une skill

Une skill est un dossier contenant au minimum un fichier SKILL.md : un en-tête (nom et description) suivi des instructions. Le dossier peut aussi contenir des documents de référence, des modèles et des scripts.

.claude/skills/compte-rendu-reunion/SKILL.md 
---
name: compte-rendu-reunion
description: Rédige un compte rendu de réunion selon la charte interne. À utiliser quand l'utilisateur fournit des notes ou une transcription de réunion.
---

# Compte rendu de réunion

1. Extraire : décisions, actions (qui / quoi / quand), points ouverts.
2. Remplir le modèle `modele.md` situé dans ce dossier.
3. Relire : chaque action a un responsable et une date.

Chargement progressif (progressive disclosure)

CoucheContenuQuand c'est chargé
1 · MétadonnéesNom + description (quelques dizaines de tokens)Toujours, au démarrage
2 · InstructionsCorps de SKILL.mdQuand la tâche correspond à la description
3 · RessourcesFichiers liés, modèles, scriptsSeulement si les instructions les demandent

Outil, skill, CLAUDE.md : lequel choisir ?

Un outil donne une capacité, une skill une procédure, CLAUDE.md des règles valables à chaque session (chapitre 16). Le tableau complet des mécanismes est au chapitre 18.

Écrire une skill efficace

  • La description est le déclencheur. C'est la seule partie que le modèle voit en permanence : elle doit dire ce que fait la skill et quand l'utiliser, avec les mots que l'utilisateur emploierait. Une description vague = skill jamais déclenchée ou déclenchée à tort.
  • Corps court, références séparées. Garde SKILL.md concis (la procédure, moins de 500 lignes selon la documentation) et déporte le volumineux (guides détaillés, exemples) dans des fichiers liés : ils ne coûtent rien tant qu'ils ne sont pas lus.
  • Scripts pour le déterministe. Pour ce qui doit être exact (conversion, validation, génération de fichier), fournis un script que l'agent exécute : son code n'entre pas dans le contexte, seule sa sortie y entre.
  • Un exemple de bon résultat vaut dix lignes de consignes.
  • Tester comme du code : lance la skill sur des cas réels, observe où l'agent hésite, et reformule. Teste aussi qu'elle ne se déclenche pas hors sujet.
Sécurité

Une skill peut contenir des scripts exécutés avec tes droits et des instructions suivies par l'agent. Traite une skill externe comme un logiciel tiers : lis tout son contenu avant de l'installer, notamment les scripts et toute instruction qui touche au réseau ou aux secrets.

Les skills se partagent en les versionnant dans Git (dossier de projet) ou en les distribuant via des plugins (chapitre 18).

À retenir
  • Un outil donne une capacité ; une skill transmet un savoir-faire.
  • Chargement progressif : description toujours chargée, instructions à la demande, ressources si besoin.
  • La description est le déclencheur : dis ce que fait la skill et quand l'utiliser.
  • Traite une skill externe comme un logiciel tiers : lis-la avant de l'installer.
