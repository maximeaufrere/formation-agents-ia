Commandes, skills, sous-agents et plugins

Personnaliser Claude Code et partager des savoir-faire avec l'équipe.

Claude Code se personnalise avec quatre mécanismes, que tu connais déjà sur le principe :

Commandes « / »

Raccourcis que tu tapes toi-même. Intégrées (/help, /clear, /compact, /init, /model, /usage, /resume) ou écrites par toi.

Skills

Procédures que Claude charge tout seul quand la tâche s'y prête (chapitre 11).

Sous-agents

Assistants spécialisés au contexte séparé, auxquels Claude délègue (chapitre 12).

Plugins

Paquets qui regroupent commandes, skills, sous-agents, hooks et serveurs MCP, pour les installer en une fois.

Tape / dans une session pour voir toutes les commandes disponibles.

Créer une commande personnalisée

Un fichier Markdown dans .claude/commands/ devient une commande. Le contenu est le prompt ; $ARGUMENTS reçoit ce que tu tapes après le nom. Les commandes ont depuis été fusionnées avec les skills : .claude/commands/revue.md et .claude/skills/revue/SKILL.md créent la même commande /revue, et les fichiers de commandes existants continuent de fonctionner. La documentation recommande les skills pour les nouveaux usages (fichiers annexes, chargement automatique).

.claude/commands/revue.md 
---
description: Relit les modifications en cours
---
Relis les modifications non commitées (git diff) pour : $ARGUMENTS
Liste les bogues probables, les cas limites non testés et les problèmes de lisibilité.
Ne modifie aucun fichier.

Usage : /revue la gestion des erreurs.

Créer un sous-agent

Un fichier Markdown dans .claude/agents/ décrit un spécialiste : son nom, sa description (quand le solliciter), les outils autorisés et éventuellement le modèle. Demande à Claude de créer ou gérer des sous-agents, ou édite directement ces dossiers : la commande /agents affiche désormais ce rappel au lieu d'ouvrir un assistant.

.claude/agents/relecteur.md 
---
name: relecteur
description: Relit du code modifié. À utiliser après une modification importante.
tools: Read, Grep, Glob, Bash
model: sonnet
---
Tu es un relecteur de code exigeant. Examine les changements récents (git diff).
Renvoie une liste courte classée par gravité, avec fichier et ligne pour chaque remarque.
N'écris jamais dans les fichiers.

Où ranger quoi ?

Dans le dossier .claude/ du projet (partagé via Git) ou dans ~/.claude/ (personnel). Les skills vont dans .claude/skills/<nom>/SKILL.md.

  • Sous-agents : chacun a sa propre fenêtre de contexte et ses outils restreints. Le coordinateur décide de déléguer d'après la description : soigne-la (quand l'utiliser, quel résultat attendre). Les sous-agents peuvent tourner en parallèle, au prix d'une consommation de tokens plus élevée (chapitre 12).
  • Choix du modèle par sous-agent : un petit modèle rapide pour la recherche ou la revue légère, un plus grand pour le raisonnement difficile : bon levier coût/qualité.
  • Plugins : un plugin contient un manifeste et des dossiers de composants. On les distribue via des « marketplaces » (dépôts Git listant des plugins). Applique les règles de chaîne d'approvisionnement : relis avant d'installer, épingle les versions.
  • Coût en contexte : les descriptions de toutes les skills, commandes et sous-agents chargés occupent de la place en permanence. N'active que ce qui sert.
À retenir
  • Commandes, skills, sous-agents, plugins : quatre façons de personnaliser Claude Code.
  • Règle sans exception : hook ou permission. Règle de chaque session : CLAUDE.md.
  • Un sous-agent isole une recherche volumineuse ; un plugin distribue le tout à l'équipe.
  • Les descriptions chargées occupent du contexte : n'active que ce qui sert.

Hooks : des automatisations garanties

Exécuter du code à des moments précis du cycle de vie, de façon déterministe.

Un hook (« crochet ») est une commande que Claude Code exécute automatiquement à un moment précis : avant ou après l'utilisation d'un outil, quand tu envoies un message, quand Claude a fini de répondre…

Analogie : la ceinture de sécurité vs le conseil de prudence

Écrire « formate toujours le code » dans CLAUDE.md, c'est un conseil : Claude l'oubliera parfois. Un hook qui lance le formateur après chaque modification, c'est une ceinture : ça se produit à chaque fois, quoi que pense le modèle.

Exemples utiles : formater le code après chaque édition, bloquer certaines commandes dangereuses, lancer les tests quand Claude termine, envoyer une notification quand il attend ta réponse, journaliser les actions pour audit.

Les principaux moments (événements)

ÉvénementQuandUsage typique
PreToolUseAvant l'exécution d'un outilBloquer ou valider une commande
PostToolUseAprès l'exécution d'un outilFormater, linter, journaliser
UserPromptSubmitQuand tu envoies un messageAjouter du contexte, filtrer
NotificationQuand Claude t'attendAlerte sonore ou message
Stop / SubagentStopQuand Claude (ou un sous-agent) a finiLancer les tests, vérifier
PreCompactAvant la compaction du contexteSauvegarder des informations
SessionStart / SessionEndDébut / fin de sessionCharger l'état, nettoyer

Il existe d'autres événements (par exemple PermissionRequest, PostToolUseFailure, SubagentStart, PostCompact, ConfigChange) : consulte la documentation officielle pour la liste à jour.

Configuration

Dans un fichier de réglages, on associe un événement, un filtre sur le nom de l'outil (matcher) et une commande :

.claude/settings.json 
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command",
            "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write" }
        ]
      }
    ]
  }
}

Le hook reçoit en entrée standard un document JSON décrivant l'événement (outil, arguments, session). La commande /hooks permet de les consulter.

Contrôler Claude depuis un hook

  • Code de sortie 0 : succès, on continue.
  • Code de sortie 2 : blocage. Pour PreToolUse, l'outil n'est pas exécuté ; le contenu de stderr est renvoyé à Claude, qui peut ajuster sa démarche. Pour Stop, Claude est empêché de s'arrêter et poursuit son travail.
  • Sortie JSON : un hook peut aussi renvoyer un objet JSON pour des décisions fines (autoriser, refuser, demander confirmation, ajouter du contexte).
  • Rapport avec les permissions : un hook qui bloque (code 2) agit avant les règles allow. À l'inverse, un hook qui répond « autoriser » ne contourne jamais une règle deny ou ask.

Exemple : garde-fou contre les commandes destructrices

.claude/hooks/garde.py (déclaré en PreToolUse, matcher « Bash ») 
import json, sys

data = json.load(sys.stdin)                     # événement reçu en JSON
cmd = data.get("tool_input", {}).get("command", "")

INTERDITS = ("rm -rf /", "git push --force", "DROP TABLE")
if any(motif in cmd for motif in INTERDITS):
    print("Commande bloquée par la politique du projet.", file=sys.stderr)
    sys.exit(2)                                 # 2 = bloquer, message renvoyé à Claude
sys.exit(0)

Bonnes pratiques et pièges

  • Les hooks s'exécutent avec tes droits, sans validation. Un hook malveillant (ou un dépôt cloné qui en apporte) peut tout faire. Relis les hooks d'un projet avant d'ouvrir une session dedans.
  • Rapides et idempotents : un hook lent ralentit chaque action ; un hook relancé deux fois ne doit rien casser. Prévois des délais d'attente.
  • Filtre étroit : utilise matcher pour ne déclencher que sur les outils concernés.
  • Ne pas dupliquer la sandbox : un hook qui filtre des chaînes de caractères est contournable (autre syntaxe, autre commande équivalente). Pour une garantie forte, combine hook, règles deny et sandbox.
  • Sorties lisibles : les messages renvoyés à Claude doivent dire quoi faire à la place (« utilise un chemin précis »), pas seulement « interdit ».
  • Cas avancés : un hook Stop qui lance la suite de tests et renvoie les échecs force Claude à continuer jusqu'au vert : c'est la boucle de vérification, rendue obligatoire.
À retenir
  • Un hook est une commande exécutée par le programme à un événement précis, sans dépendre du modèle.
  • Code de sortie 2 : sur les événements qui peuvent bloquer (PreToolUse, Stop...), l'action est bloquée et le message revient à Claude. Les autres codes non nuls (comme 1) ne bloquent pas : pour imposer une règle, utilise 2.
  • Un hook s'exécute avec tes droits : relis ceux d'un dépôt avant d'y ouvrir une session.
  • Un hook Stop qui lance les tests force Claude à continuer jusqu'au vert.

MCP dans Claude Code

Brancher Claude Code à tes outils (tickets, bases, documentation) de façon sûre.

Grâce à MCP (chapitre 10), Claude Code peut sortir de ton dépôt : lire un ticket, consulter la documentation interne, interroger une base de données de test, créer une pull request. On « branche » un serveur MCP avec une commande, puis ses outils apparaissent dans la session.

Exemples de demandes rendues possibles : « Lis le ticket PROJ-123 et implémente-le », « Compare ce schéma avec la base de préproduction », « Résume les erreurs remontées par l'outil de supervision cette nuit ».

Rappel de sécurité

Chaque serveur connecté donne un pouvoir de plus à l'agent. Branche seulement des serveurs de confiance et, au départ, avec un accès en lecture seule.

Ajouter un serveur

# Serveur distant (HTTP)
claude mcp add --transport http mon-service https://exemple.com/mcp

# Serveur local (processus lancé par Claude Code, transport stdio)
claude mcp add --env DB_URL=postgres://lecture-seule@localhost/test --transport stdio ma-base -- npx -y serveur-mcp-base

claude mcp list          # voir les serveurs configurés
/mcp                     # dans la session : état, authentification (OAuth)

Trois portées de configuration

PortéeStockageUsage
local (défaut)Privé, propre à toi et à ce projetEssais, identifiants personnels
projectFichier .mcp.json à la racine, versionnéServeurs partagés par l'équipe (approbation demandée à l'ouverture)
userConfig personnelle, tous projetsOutils que tu utilises partout

Les outils d'un serveur sont nommés mcp__serveur__outil : on peut donc écrire des règles de permission précises (allow pour la lecture, ask pour l'écriture).

Partager la configuration d'équipe

.mcp.json (racine du projet) 
{
  "mcpServers": {
    "tickets": {
      "type": "http",
      "url": "https://tickets.exemple.com/mcp"
    },
    "base-test": {
      "command": "npx",
      "args": ["-y", "serveur-mcp-base"],
      "env": { "DB_URL": "${DB_URL_TEST}" }
    }
  }
}

Les variables d'environnement (${DB_URL_TEST}) évitent de versionner des secrets : chaque développeur fournit les siens.

  • Coût en contexte : comme pour tout serveur MCP (chapitre 10, niveau 3), les définitions d'outils occupent le contexte : désactive les serveurs inutiles pour la tâche. Par défaut, Claude Code charge les outils MCP à la demande (tool search) : seuls leurs noms occupent le contexte au démarrage. Sur certains modèles anciens ou déploiements, ou si tu désactives cette option (ENABLE_TOOL_SEARCH=false), toutes les définitions sont chargées d'avance.
  • Taille des sorties : au-delà de 10 000 tokens, Claude Code avertit ; au-delà de 25 000 tokens par défaut, il enregistre le résultat dans un fichier au lieu de l'injecter dans la conversation. Même ainsi, de gros résultats coûtent du contexte : un serveur bien conçu pagine et filtre.
  • Moindre privilège : jeton en lecture seule pour la base de test, jamais les identifiants de production, portée minimale pour les API (principe : chapitre 13).
  • Confiance et injection : le contenu récupéré via MCP est une donnée non fiable (chapitre 13) : vérifie les actions qui en découlent.
  • Approbation des serveurs de projet : un .mcp.json versionné lance du code sur ta machine ; examine-le avant d'accepter, notamment après un git pull qui le modifie.
  • Écrire ton propre serveur : quand l'outil n'existe pas, un petit serveur (voir le chapitre 10 niveau 3) qui expose 3 ou 4 opérations ciblées vaut mieux qu'un accès générique à toute l'API.
À retenir
  • claude mcp add branche un serveur (HTTP distant ou stdio local).
  • Trois portées : local, project (.mcp.json versionné), user.
  • Les outils se nomment mcp__serveur__outil : des permissions fines sont possibles.
  • Le contenu récupéré via MCP est une donnée non fiable ; jetons à portée minimale.
