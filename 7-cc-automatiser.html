Automatisation : mode non interactif, SDK et CI

Utiliser Claude Code dans des scripts, des pipelines et des programmes.

Claude Code n'est pas réservé au chat dans un terminal. Avec l'option -p (« print »), tu lui donnes une consigne, il travaille sans interaction, affiche le résultat et rend la main. On peut donc l'intégrer à des scripts, des tâches planifiées ou des chaînes d'intégration continue.

claude -p "Résume les changements de la dernière semaine dans ce dépôt"
  • Revue automatique des pull requests.
  • Génération de notes de version ou de documentation.
  • Tri d'issues, correction de petites erreurs de lint, mises à jour de dépendances.
Sans humain pour valider

En mode non interactif, personne ne clique « autoriser ». Il faut donc déclarer à l'avance exactement ce qui est permis, et rien de plus.

Options utiles

OptionEffet
-p "consigne"Exécution non interactive.
--output-format json (ou stream-json)Sortie structurée exploitable par un programme (résultat, coût, identifiant de session).
--allowedToolsListe des outils autorisés sans demande (ex. lecture + une commande précise).
--max-turnsPlafond de tours de boucle (mode non interactif).
--continue / --resumeReprendre la dernière session ou une session précise.
--permission-modeMode de départ (acceptEdits, dontAsk, auto…). En automatisation, dontAsk refuse tout ce qui n'est pas autorisé d'avance.
--bareDémarrage minimal : ignore hooks, skills, plugins, serveurs MCP et CLAUDE.md. Recommandé pour les scripts et la CI. Il n'utilise pas ton abonnement : fournis ANTHROPIC_API_KEY.
 
# Revue d'un diff, résultat en JSON
git diff main | claude -p "Relis ce diff et liste les risques" --output-format json

# Correction ciblée avec droits minimaux et plafond de tours
claude -p "Corrige les erreurs de lint" \
  --allowedTools "Read" "Edit" "Bash(npm run lint *)" \
  --max-turns 8

Intégration continue

Une action GitHub officielle permet de mentionner @claude dans une issue ou une pull request pour lui confier une tâche, ou de déclencher des revues automatiques. Les mêmes principes s'appliquent à d'autres systèmes d'intégration continue.

Le SDK d'agent : la boucle, par programmation

Le SDK Claude Agent (Python et TypeScript) expose la même boucle et les mêmes outils que Claude Code, pour construire tes propres agents : tu définis les instructions, les outils autorisés, les serveurs MCP, les hooks, puis tu consommes un flux de messages.

agent_todo.py 
import asyncio
from claude_agent_sdk import query, ClaudeAgentOptions

async def main():
    options = ClaudeAgentOptions(
        allowed_tools=["Read", "Grep", "Glob"],     # approuvés sans demande (ne restreint pas les autres outils)
        max_turns=6,
    )
    async for message in query(prompt="Liste les TODO du dépôt par fichier",
                               options=options):
        print(message)

asyncio.run(main())

Exploiter Claude Code en production

  • Dépôt non fiable : sans --bare, claude -p exécute les hooks de .claude/settings.json et connecte les serveurs de .mcp.json du dossier, sans dialogue de confiance. Sur du code externe, ajoute --bare et fournis seulement ce qu'il faut (--settings, --mcp-config).
  • Droits minimaux en CI : jeton à portée minimale, --allowedTools restreint, aucun secret inutile dans l'environnement, exécution dans un conteneur éphémère. Un pipeline qui lit des issues ou des PR externes expose l'agent à l'injection de prompt : n'y donne ni secrets ni droits d'écriture larges.
  • Sorties structurées : exploite le JSON (champ de résultat, coût, durée) pour décider de la suite, journaliser et refuser les résultats incomplets.
  • Budget et limites : --max-turns, délai d'expiration du job, alerte sur le coût par exécution.
  • Parallélisme : pour lancer plusieurs agents sur le même dépôt sans conflits, donne à chacun sa propre copie de travail (git worktree).
  • Idempotence et relecture : l'agent propose (branche, pull request), un humain ou un contrôle automatique valide la fusion. Évite que l'agent pousse directement sur la branche principale.
  • Reproductibilité : épingle la version de Claude Code et du modèle dans les jobs récurrents, et rejoue un jeu de tâches avant toute montée de version.
À retenir
  • claude -p exécute sans interaction : scripts, tâches planifiées, CI.
  • Sans humain pour valider, déclare à l'avance ce qui est permis.
  • Le SDK d'agent expose la même boucle en Python et en TypeScript.
  • En CI : droits minimaux, plafond de tours, sortie JSON. L'agent propose, un humain fusionne.

Méthodes de travail et bonnes pratiques

Obtenir de bons résultats de façon régulière avec Claude Code, et éviter les pièges.

La méthode en quatre temps
  1. Explorer : demande à Claude de lire et de t'expliquer le code concerné (sans rien modifier).
  2. Planifier : en mode plan, fais proposer l'approche, discute-la, corrige-la.
  3. Coder : valide le plan, laisse Claude implémenter.
  4. Valider : lance les tests, relis les changements, fais-les commiter.

Cinq réflexes

  • Donne-lui un moyen de vérifier (tests, commande de build, capture d'écran attendue). C'est un conseil particulièrement utile.
  • Sois précis : fichiers concernés, comportement attendu, exemple.
  • Petits pas : une tâche à la fois, un commit par étape.
  • /clear entre deux tâches sans rapport pour repartir avec un contexte propre.
  • Relis toujours ce qui sera livré : tu restes responsable.

Mauvaise et bonne demande

Trop vague

« Améliore la page de connexion. »

Précis et vérifiable

« Dans @src/login.tsx, affiche un message d'erreur sous le champ mot de passe quand l'API renvoie 401. Ajoute un test dans login.test.tsx et lance-le. »

Trois workflows éprouvés

  • Explorer → planifier → coder → commiter. Idéal pour une fonctionnalité nouvelle : le plan écrit sert de point de contrôle avant de toucher au code.
  • Test d'abord (TDD). Demande d'écrire des tests qui échouent pour le comportement voulu, commite-les, puis laisse Claude coder jusqu'à ce qu'ils passent, sans modifier les tests. La cible est objective, la boucle de vérification est prête.
  • Correction depuis un symptôme. Colle l'erreur, les logs, ou une capture d'écran ; demande de reproduire le problème par un test avant de corriger.

Gérer le contexte

  • Surveille le remplissage de la session (voir les chapitres 3 et 9).
  • /compact avec des consignes (« garde la liste des fichiers modifiés et les décisions ») avant de poursuivre une longue tâche.
  • /clear entre les sujets ; /resume pour retrouver une session.
  • Pour une investigation qui lit beaucoup de fichiers, demande de la déléguer à un sous-agent : seul le résumé revient dans ta session.

Travailler en parallèle

Ouvre plusieurs sessions sur des tâches indépendantes, chacune dans son propre worktree Git (copie de travail séparée du même dépôt). Les modifications ne se marchent pas dessus, et chaque session garde son contexte propre.

Principes d'expert

  • Investis dans le harnais, pas seulement dans le prompt. La qualité vient de l'environnement : tests rapides et fiables, linter, typage, CLAUDE.md concis, hooks de vérification, commandes d'amorçage. Un projet bien outillé multiplie l'efficacité de l'agent.
  • Séparer l'auteur et le relecteur. Une seconde session (ou un sous-agent) au contexte vierge relit le diff : elle n'est pas biaisée par le raisonnement de l'auteur, ce qui améliore la relecture. Variante : une session écrit les tests, une autre le code.
  • Spécifier l'intention, pas la procédure. Décris le résultat et les contraintes ; laisse l'agent choisir les étapes. Excès de micro-gestion = perte de ses capacités d'adaptation.
  • Mesurer. Suis le taux de changements acceptés sans reprise, le temps de cycle, le coût par tâche. Compare les approches (avec/sans plan, avec/sans sous-agent) sur vos propres tâches.
  • Capitaliser. Chaque erreur répétée devient soit une ligne de CLAUDE.md, soit un hook, soit une commande/skill. L'équipe progresse collectivement.

La posture à adopter

Traite Claude Code comme un développeur talentueux, rapide, mais sans mémoire de ton projet et sans accès à ton intuition métier : donne-lui le contexte (CLAUDE.md), un objectif clair, des moyens de vérifier son travail, et garde la responsabilité de ce qui est livré.

À retenir
  • Quatre temps : explorer, planifier, coder, valider.
  • Donne un moyen de vérifier : tests, build, critères d'acceptation.
  • /clear entre deux tâches ; un sous-agent pour les lectures volumineuses.
  • Investis dans le harnais (tests, linter, CLAUDE.md, hooks), pas seulement dans le prompt.
