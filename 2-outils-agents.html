Outils et agents

Comment un modèle agit sur le monde grâce à des outils, ce qu'est la boucle d'un agent, et quand préférer un workflow.

06

Les outils : donner des mains au modèle

Comprendre comment un modèle « appelle » une application, jusqu'au format exact des messages.

Un outil (tool) est une fonction que le modèle peut demander à utiliser : chercher sur le web, lire un fichier, interroger une base, envoyer un email, exécuter du code, créer un ticket…

Point essentiel : le modèle n'exécute rien lui-même. Il écrit une demande structurée (« appelle chercher_salles avec date=mardi »). Le programme qui l'entoure exécute réellement l'outil et renvoie le résultat, que le modèle lit avant de continuer.

Le modèle décide, le programme exécute.

Comment le modèle connaît les outils

À chaque appel, on lui transmet la liste des outils disponibles, chacun décrit par un nom, une description en langage naturel et un schéma JSON des paramètres. Le modèle décide, d'après l'objectif et ces descriptions, s'il répond directement ou s'il appelle un outil, et avec quels arguments.

Deux familles d'outils

  • Outils côté client : tu les codes et les exécutes (accès à ta base, à ton CRM). Tu renvoies le résultat au modèle.
  • Outils côté serveur : fournis et exécutés par le fournisseur (recherche web, exécution de code). Le résultat revient directement dans la réponse.

Détails qui comptent

  • Le modèle peut demander plusieurs outils en parallèle dans une même réponse (par exemple lire trois fichiers).
  • Quand un outil échoue, renvoie l'erreur au modèle sous forme de texte clair : il saura souvent corriger (mauvais paramètre, fichier introuvable).
  • Les outils sont la principale surface de risque : ce que l'outil peut faire, l'agent peut le faire (chapitre 13).

Le protocole exact (API Messages)

1) Tu déclares l'outil avec un schéma :

définition de l'outil 
{
  "name": "chercher_salles",
  "description": "Liste les salles de réunion libres pour une date. Renvoie nom et capacité.",
  "input_schema": {
    "type": "object",
    "properties": {
      "date":       { "type": "string",  "description": "Date au format AAAA-MM-JJ" },
      "places_min": { "type": "integer", "description": "Capacité minimale" }
    },
    "required": ["date"]
  }
}

2) Le modèle répond avec stop_reason: "tool_use" et un bloc de demande :

{ "type": "tool_use", "id": "toolu_01A", "name": "chercher_salles",
  "input": { "date": "2026-10-27", "places_min": 8 } }

3) Tu exécutes la fonction, puis tu renvoies un message utilisateur avec le résultat, lié par l'identifiant :

{ "type": "tool_result", "tool_use_id": "toolu_01A",
  "content": "Rhône (10 places), Saône (8 places)" }

Concevoir de bons outils (l'« interface agent-ordinateur »)

  • Peu d'outils, bien nommés. Trop d'outils proches dégradent le choix du modèle et coûtent des tokens à chaque appel. Regroupe ou préfixe par domaine (tickets_creer, tickets_chercher).
  • Descriptions écrites comme pour un nouveau collègue : quand l'utiliser, quand ne pas l'utiliser, format des paramètres, exemples.
  • Résultats compacts et utiles : renvoie des noms lisibles plutôt que des identifiants opaques, pagine, tronque, et explique comment affiner (« 200 résultats, ajoute un filtre »).
  • Messages d'erreur actionnables : « date invalide, attendu AAAA-MM-JJ » plutôt que « erreur 400 ».
  • Idempotence et sécurité : une action répétée par erreur (envoyer deux fois un email) ne doit pas faire de dégâts ; les actions destructrices demandent une confirmation.
  • Contrôle du choix : le paramètre tool_choice accepte quatre valeurs : auto (le modèle décide, valeur par défaut), any (impose un outil parmi ceux fournis), tool (force un outil précis) et none (interdit les outils). Attention : sur les modèles Claude les plus récents (par exemple Sonnet 5.5 et Opus 5.5), any et tool renvoient une erreur 400. On garde alors auto et on ajoute strict: true sur l'outil pour garantir des paramètres conformes au schéma.
À retenir
  • Le modèle n'exécute rien : il demande un outil, le programme l'exécute et renvoie le résultat.
  • Un outil = un nom, une description, un schéma JSON des paramètres.
  • Peu d'outils, bien décrits, avec des erreurs lisibles.
  • Les outils sont la principale surface de risque.

Suite : Chapitre 7 · L'agent et sa boucle

07

L'agent : un modèle, des outils, une boucle

Définir un agent et décrire son fonctionnement pas à pas, jusqu'au code de la boucle.

Définition

Un agent IA = un modèle (LLM) + des outils + un contexte + une boucle qui continue jusqu'à ce que l'objectif soit atteint (ou qu'une limite soit rencontrée).

La boucle agentique.

Démo 2 · Regarder un agent travailler

Objectif donné : « Réserve une salle de 8 personnes mardi après-midi et préviens l'équipe. »

    À l'étape 6, la salle choisie était déjà prise. Un simple script aurait planté. L'agent a lu l'erreur, changé de stratégie et réessayé : c'est ce qui le distingue d'une automatisation figée.

    Ce qui se passe à chaque tour

    1. Le programme envoie au modèle : consignes système, définitions d'outils, historique complet.
    2. Le modèle répond soit par du texte final, soit par une ou plusieurs demandes d'outils.
    3. S'il y a des demandes d'outils, le programme les exécute, ajoute les résultats à l'historique, et retourne à l'étape 1.
    4. Sinon la boucle s'arrête.

    Conditions d'arrêt

    • Succès : le modèle juge l'objectif atteint (idéalement après une vérification).
    • Limite de tours ou de budget : indispensable, pour éviter les boucles infinies et les factures surprises.
    • Blocage : le modèle demande une précision ou une autorisation à l'humain.
    • Erreur irrécupérable ou interruption par l'utilisateur.

    Planification et auto-correction

    Pour les tâches longues, on demande à l'agent de tenir une liste de tâches (qu'il met à jour) et de vérifier son travail avant de conclure (relancer les tests, relire le résultat). Les agents qui se vérifient échouent souvent moins que ceux qui s'arrêtent à leur première tentative.

    La boucle en code

    Toute la « magie » d'un agent tient en quelques lignes. Les frameworks ajoutent surtout de la robustesse (reprise sur erreur, journalisation, parallélisme).

    boucle_agent.py 
    messages = [{"role": "user", "content": objectif}]

for tour in range(MAX_TOURS):                      # plafond dur : jamais de boucle infinie
    rep = client.messages.create(
        model=MODEL, max_tokens=2048,
        system=SYSTEME, tools=OUTILS, messages=messages,
    )
    messages.append({"role": "assistant", "content": rep.content})

    if rep.stop_reason != "tool_use":              # plus d'outil demandé : réponse finale
        break

    resultats = []
    for bloc in rep.content:
        if bloc.type == "tool_use":
            try:
                sortie = executer(bloc.name, bloc.input)    # TON code, avec garde-fous
            except Exception as e:
                sortie = f"Erreur : {e}"                    # l'erreur revient au modèle
            resultats.append({"type": "tool_result",
                              "tool_use_id": bloc.id,
                              "content": str(sortie)[:20000]})   # borne la taille
    messages.append({"role": "user", "content": resultats})

    Points d'ingénierie

    • Gestion du contexte : borne la taille des sorties d'outils (comme dans le code ci-dessus) ; pour résumer ou élaguer l'historique, voir le chapitre 9.
    • Reprise : persister l'historique et l'état pour reprendre après une panne ; rendre les outils idempotents.
    • Observabilité : journaliser chaque appel (entrée, sortie, durée, tokens). Sans trace, impossible de comprendre un échec.
    • Évaluer un agent : mesurer le résultat final (la tâche est-elle réussie ?) et la trajectoire (nombre d'étapes, outils superflus, erreurs). Rejouer les mêmes tâches avant et après chaque changement.
    • Coût : les agents consomment typiquement plusieurs fois plus de tokens qu'une simple conversation. Fixe un budget par tâche.
    À retenir
    • Un agent = un modèle + des outils + un contexte + une boucle (réfléchir, agir, observer).
    • Toujours une limite de tours ou de budget.
    • Il se corrige en lisant l'erreur renvoyée, là où un script figé planterait.
    • Mesure le résultat final et la trajectoire (étapes, outils superflus).

    08

    Chatbot, workflow ou agent ?

    Choisir le bon niveau d'autonomie pour un besoin donné.

    « Agent » est devenu un mot à la mode, appliqué à tout. Plus d'autonomie veut dire plus de puissance, mais aussi plus d'imprévisibilité et de coût.

    ChatbotWorkflow assisté par IAAgent
    Qui décide des étapes ?Personne : une seule réponseToi, en amont (étapes fixes)Le modèle, en cours de route
    OutilsAucun ou peuAppelés à des endroits prévusChoisis et enchaînés librement
    PrévisibilitéÉlevéeÉlevéeMoyenne à faible
    ExempleFAQ intelligenteChaque facture reçue : extraire, classer, enregistrer« Enquête sur cette baisse de ventes et propose un plan »
    Conseil de praticien

    Commence par la solution la plus simple qui marche. Si les étapes sont connues d'avance, un workflow est plus fiable, plus rapide et moins cher qu'un agent.

    Cinq schémas de workflow à connaître

    SchémaPrincipeQuand l'utiliser
    Enchaînement (prompt chaining)La sortie d'une étape alimente la suivante, avec des contrôles intermédiaires.Tâche décomposable en étapes claires (rédiger puis traduire).
    RoutageUne première étape classe la demande et l'oriente vers un traitement spécialisé.Types de demandes très différents (facturation, technique, commercial).
    ParallélisationPlusieurs appels simultanés : sous-tâches indépendantes ou « votes ».Gagner du temps ou fiabiliser par consensus.
    Coordinateur et sous-agentsUn modèle découpe dynamiquement la tâche et délègue.Sous-tâches non prévisibles (modifier plusieurs fichiers).
    Évaluateur-optimiseurUn modèle produit, un autre critique, on itère.Critères de qualité clairs (traduction, code, rédaction).

    L'agent « pur » vient s'ajouter quand aucun de ces schémas ne suffit parce que le chemin dépend de ce qu'on découvre.

    Grille de décision

    QuestionSi oui, penche vers…
    Les étapes sont-elles connues et stables ?Workflow codé (voire sans IA pour la partie déterministe)
    Le volume est-il élevé et le coût unitaire critique ?Workflow avec petit modèle, étapes courtes
    Peut-on vérifier automatiquement le résultat ?Agent avec boucle de vérification (tests, validations)
    Une erreur est-elle coûteuse ou irréversible ?Workflow ou agent avec validation humaine avant l'effet
    La latence doit-elle rester sous quelques secondes ?Pas d'agent multi-tours en temps réel
    Le chemin dépend de ce qu'on trouve en cours de route ?Agent
    • Hybride : de nombreux systèmes robustes sont des workflows dans lesquels certaines étapes sont des agents bornés (budget, outils limités).
    • Montée progressive : démarre en workflow, mesure où il échoue faute de flexibilité, et n'ouvre l'autonomie que sur ces zones.
    • Coût total : compare le coût par tâche réussie (tokens + relectures humaines + reprises), pas seulement le coût par appel.
    À retenir
    • Plus d'autonomie = plus de puissance, mais plus d'imprévisibilité et de coût.
    • Étapes connues d'avance : workflow. Chemin qui dépend de ce qu'on découvre : agent.
    • Cinq schémas de workflow : enchaînement, routage, parallélisation, coordinateur et sous-agents, évaluateur-optimiseur.
    • Commence par la solution la plus simple qui marche.
