Claude Code : prise en main

Comprendre ce qu'est Claude Code, comment il fonctionne et le lancer pour la première fois.

Claude Code est l'agent de programmation d'Anthropic. Tu le lances dans un dossier de projet, tu lui décris une tâche en langage naturel (« corrige le test qui échoue », « ajoute un filtre par date à cette page »), et il lit ton code, modifie les fichiers, exécute des commandes et vérifie le résultat. C'est exactement la boucle des chapitres 6 et 7, avec des outils taillés pour le développement.

Une image pour retenir

C'est un collègue développeur assis dans ton terminal : il explore le projet, propose une modification, te demande l'autorisation avant les actions sensibles, et lance les tests pour vérifier son travail.

Où l'utiliser

  • Dans un terminal (usage de référence), dans le dossier de ton projet.
  • Dans un éditeur via les extensions (VS Code, JetBrains).
  • Application de bureau et web, selon les offres.

Premier lancement

cd mon-projet
claude                      # démarre une session interactive
> Explique-moi l'architecture de ce projet

À la première utilisation, il te propose de te connecter (compte Claude ou clé d'API d'organisation). L'installation exacte évolue : suis la documentation officielle de Claude Code.

    Ce que Claude Code charge dans son contexte

    • Son prompt système et les définitions de ses outils.
    • Tes fichiers d'instructions CLAUDE.md (chapitre 16).
    • Les fichiers qu'il lit, les sorties de commandes, l'historique de la session.

    Il n'indexe pas ton dépôt à l'avance : il cherche à la demande avec Read et des recherches par motif (Glob, Grep, ou find et grep selon la plateforme), comme le ferait un développeur qui découvre le projet.

    Gestes de base

    • Écrire @chemin/fichier pour désigner un fichier précis.
    • Préfixer par ! pour lancer directement une commande shell.
    • Échap pour interrompre ; /clear pour repartir d'un contexte vide ; /resume pour reprendre une session.
    • /model pour changer de modèle ; /usage pour voir la consommation (alias : /cost).

    Architecture : la boucle du chapitre 7, en production

    ┌────────────────────── session Claude Code ───────────────────────┐
│ contexte = prompt système + outils + CLAUDE.md + historique       │
│                                                                   │
│  modèle ──demande d'outil──▶ moteur de permissions ──▶ exécution  │
│     ▲                         (règles, mode, hooks)     (Read/Edit/Bash/MCP)
│     └──────────── résultat (tronqué si trop long) ◀───────────────┘
└───────────────────────────────────────────────────────────────────┘
    • Le moteur de permissions se place entre le modèle et l'exécution : chaque appel d'outil passe par les règles allow/ask/deny, le mode courant et d'éventuels hooks (chapitres 17 et 19).
    • Gestion automatique du contexte : quand la fenêtre approche de sa limite, la conversation est compactée. Tu peux aussi déclencher /compact avec des instructions sur ce qu'il faut conserver.
    • Prompt caching : le préfixe stable (système, outils, CLAUDE.md) est mis en cache, ce qui réduit coût et latence des tours successifs. Modifier CLAUDE.md ou la liste des outils en cours de session peut invalider ce cache.
    • Authentification et déploiement : compte Claude (abonnement), clé d'API Anthropic, ou fournisseurs cloud (Amazon Bedrock, Google Cloud, Microsoft Foundry) pour les entreprises qui imposent leur cloud.
    • Extensibilité : la même boucle se pilote par code (mode non interactif, SDK, chapitre 21), s'étend par MCP (chapitre 20), skills et sous-agents (chapitre 18), hooks (chapitre 19).
    • Télémétrie d'équipe : des métriques d'usage et de coût peuvent être exportées (par exemple au format OpenTelemetry) pour piloter l'adoption et le budget.
    Pourquoi ça marche bien pour le code

    Le code a un vérificateur objectif : le compilateur, le linter, les tests. L'agent peut donc agir, mesurer, corriger, sans qu'un humain valide chaque pas. C'est la leçon du chapitre 5 : la fiabilité vient de la boucle de vérification. Plus tu fournis de vérifications automatiques à ton projet, meilleur devient Claude Code.

    À retenir
    • Claude Code est un agent de programmation : la boucle des chapitres 6 et 7, avec des outils pour le code.
    • Il cherche à la demande au lieu d'indexer ton dépôt.
    • Chaque appel d'outil passe par le moteur de permissions.
    • Il réussit bien sur du code parce que tests et compilateur vérifient son travail.

    Suite : Chapitre 16 · CLAUDE.md : la mémoire du projet

    CLAUDE.md : la mémoire du projet

    Donner à Claude Code les connaissances du projet qu'il ne peut pas deviner.

    Claude Code démarre chaque session avec un contexte vide, sans souvenir de la précédente (hors les notes qu'il peut prendre seul : voir niveau 2). CLAUDE.md est un fichier texte, à la racine du projet, que Claude lit au début de chaque session. Tu y écris ce qu'un nouveau développeur devrait savoir : comment lancer les tests, les conventions de code, les pièges du projet.

    Analogie : le dossier d'accueil du nouvel arrivant

    Le jour de son arrivée, une personne reçoit les accès, la façon de lancer le projet et les règles de l'équipe. CLAUDE.md joue ce rôle pour l'agent, à chaque session.

    La commande /init analyse le projet et génère un premier CLAUDE.md que tu corriges ensuite. Commit-le dans Git : toute l'équipe en profite.

    CLAUDE.md 
    # Projet Facturation

## Commandes
- Tests : `npm run test` (un fichier : `npm run test -- src/panier.test.ts`)
- Lint : `npm run lint` (à lancer avant chaque commit)

## Conventions
- TypeScript strict, pas de `any`.
- Les montants sont des entiers en centimes, jamais des flottants.

## À savoir
- Le dossier `legacy/` est gelé : ne pas le modifier.

    Où placer les fichiers ?

    EmplacementPortéePartagé ?
    ~/.claude/CLAUDE.mdToi, tous tes projetsNon (préférences personnelles)
    ./CLAUDE.md ou ./.claude/CLAUDE.mdTout le projetOui, versionné dans Git
    ./CLAUDE.local.mdToi, ce projetNon : à mettre dans .gitignore
    sous-dossier/CLAUDE.mdCe dossier, chargé quand Claude y travailleOui
    Politique d'entreprise (gérée)Toute l'organisationImposée par l'IT

    Fonctions pratiques

    • Imports : un CLAUDE.md peut référencer d'autres fichiers (@docs/architecture.md) pour rester court tout en donnant accès au détail.
    • /memory ouvre les fichiers de mémoire pour les éditer, et permet d'activer ou non la mémoire automatique.
    • Mémoire automatique : Claude peut aussi noter seul ce qu'il apprend de tes corrections. Elle complète CLAUDE.md, elle ne le remplace pas.
    • Règles ciblées : des fichiers Markdown dans .claude/rules/ découpent les instructions par sujet ou par type de fichier.
    • Quand Claude commet deux fois la même erreur, ajoute la règle correspondante : c'est la méthode la plus simple pour l'améliorer dans la durée.

    Que mettre, que ne pas mettre ?

    À mettre
    • Commandes de build, test, lint
    • Conventions non évidentes
    • Architecture en quelques lignes
    • Pièges connus, dossiers interdits
    À éviter
    • Ce que le code montre déjà
    • Règles de style gérées par un linter
    • Longs documents recopiés
    • Informations qui changent souvent

    CLAUDE.md est du contexte, pas du code

    • Il coûte des tokens à chaque session, et chaque ligne concurrence l'attention du modèle. Un CLAUDE.md de 500 lignes est moins bien suivi qu'un de 60 ; la documentation vise moins de 200 lignes par fichier. Élague régulièrement.
    • Aucune garantie d'application. C'est une consigne que le modèle suit « le plus souvent ». Pour une règle qui doit être respectée sans exception (formater après chaque édition, interdire une commande), utilise un hook (chapitre 19) ou une règle de permission (chapitre 17).
    • Formulation : des consignes concrètes et testables (« exécute npm run lint avant de conclure ») fonctionnent mieux que des principes vagues (« écris du code propre »).
    • Emphase : si une règle critique est ignorée, reformule-la et place-la plus haut plutôt que d'empiler des majuscules.
    • Chargement hiérarchique : les fichiers des sous-dossiers ne sont lus que lorsque Claude touche à ces dossiers. Utilise-les pour les règles propres à un module, afin de ne pas alourdir le contexte global.
    • Hygiène d'équipe : relis les changements de CLAUDE.md en revue de code, comme n'importe quelle source de vérité. Une consigne erronée est exécutée à chaque session.
    Boucle d'amélioration

    Observe les sessions → repère les erreurs répétées → formule la règle manquante en une ligne → vérifie que la session suivante la respecte → sinon, passe à un hook. Ton CLAUDE.md devient la mémoire institutionnelle de l'équipe.

    À retenir
    • CLAUDE.md est lu au début de chaque session : commandes, conventions, pièges du projet.
    • /init en génère un premier ; versionne-le dans Git.
    • Court et concret : c'est une consigne, sans garantie d'application.
    • Une règle qui ne doit jamais être violée appartient à un hook ou à une permission.

    Suite : Chapitre 17 · Permissions, modes et retour arrière

    Permissions, modes et retour arrière

    Contrôler ce que Claude Code a le droit de faire, et pouvoir annuler.

    Par défaut, Claude Code demande ton accord avant de modifier un fichier ou d'exécuter une commande. Il peut lire librement, mais il ne change rien sans validation. Tu choisis, pour chaque demande, d'accepter, de refuser, ou d'autoriser ce type d'action pour la suite.

    Les modes

    Par défaut

    Demande avant d'agir

    Le plus prudent pour débuter.

    Acceptation des éditions

    Modifie sans demander

    Les éditions de fichiers passent seules. Les commandes sensibles restent soumises à validation.

    Plan

    Réfléchit, ne touche à rien

    Explore le code et propose un plan que tu valides avant toute modification.

    On change de mode en cours de session avec le raccourci Maj+Tab, ou on démarre dans un mode avec --permission-mode. Deux autres modes existent : auto (un classificateur examine les actions à ta place) et dontAsk (refuse tout ce qui demanderait une validation). Il existe aussi un mode qui contourne toutes les permissions : à réserver à des environnements jetables et isolés (voir niveau 3).

    Bon réflexe

    Pour une tâche non triviale, commence en mode plan : lis le plan, corrige-le, puis seulement après laisse Claude modifier le code. Corriger un plan coûte bien moins cher que corriger vingt fichiers modifiés.

    Retour arrière : Claude Code garde des points de contrôle des fichiers qu'il modifie avec ses outils d'édition. En cas de dérive, Échap deux fois (champ de saisie vide) ou /rewind permet de revenir à un état précédent de la session. Les fichiers changés par des commandes Bash ne sont pas suivis : Git reste ton filet de sécurité.

    Règles d'autorisation

    Pour ne pas valider cent fois la même commande sûre, tu déclares des règles dans un fichier de configuration. Trois listes : allow (autorisé sans demander), ask (toujours demander), deny (interdit).

    .claude/settings.json 
    {
  "permissions": {
    "allow": ["Bash(npm run test *)", "Bash(git diff *)", "Bash(git status)"],
    "ask":   ["Bash(git push *)"],
    "deny":  ["Read(./.env)", "Read(./secrets/**)", "Bash(curl *)"]
  }
}

    La commande /permissions permet de consulter et modifier ces règles de façon interactive.

    Où vivent les réglages ? (du plus fort au plus faible)

    1. Politique d'entreprise (gérée) : imposée, non modifiable par l'utilisateur.
    2. Option --settings de la ligne de commande, pour la session.
    3. .claude/settings.local.json : réglages personnels du projet, non versionnés.
    4. .claude/settings.json : réglages d'équipe du projet, versionnés.
    5. ~/.claude/settings.json : réglages personnels globaux.

    Sémantique des règles

    • Priorité : une règle deny l'emporte sur ask, qui l'emporte sur allow. Mets les interdictions de sécurité en deny au bon niveau (projet ou politique d'entreprise).
    • Motifs : Bash(npm run test *) autorise les commandes commençant par ce préfixe (l'écriture :* en fin de motif est équivalente) ; Read(./secrets/**) cible des chemins. Les règles sur Bash reposent sur des préfixes : elles ne remplacent pas un vrai cloisonnement. Une commande composée (enchaînée par des opérateurs) mérite une vigilance particulière.
    • Granularité par outil : les outils MCP s'adressent par nom (mcp__serveur__outil), ce qui permet d'autoriser la lecture d'un serveur et d'interdire son écriture.

    Sandbox : isoler pour de bon

    Les permissions décident si on demande. Le bac à sable décide ce qui est techniquement possible : Claude Code peut exécuter ses commandes dans un environnement restreint au niveau du système d'exploitation, avec accès limité au système de fichiers (le projet seulement) et au réseau (domaines autorisés). Même une injection de prompt réussie reste alors cantonnée.

    Le mode « contourner les permissions »

    L'option --dangerously-skip-permissions supprime toutes les validations. Son nom est volontairement dissuasif. Usage raisonnable : uniquement dans un conteneur ou une machine virtuelle jetable, sans accès à des secrets ni à un réseau ouvert, pour des tâches automatisées bornées. Jamais sur ton poste avec tes identifiants.

    Autres points de vigilance

    • Fatigue d'approbation : si tu valides tout par réflexe, la protection disparaît (chapitre 13). Autorise à l'avance les actions sûres et fréquentes.
    • Ne fais confiance à un dépôt inconnu qu'après l'avoir examiné : un projet cloné peut contenir ses propres réglages, hooks et configuration MCP.
    • Secrets : interdis la lecture des fichiers .env et des dossiers de clés via deny.
    À retenir
    • Par défaut, Claude Code demande avant de modifier un fichier ou d'exécuter une commande.
    • Pour une tâche non triviale, commence en mode plan (Maj+Tab).
    • Règles allow, ask, deny dans les réglages ; deny l'emporte toujours.
    • Les permissions décident si on demande ; le bac à sable décide ce qui est techniquement possible.
